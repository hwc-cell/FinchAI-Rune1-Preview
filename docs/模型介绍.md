## 一、这是什么

一个 1.55B 的**本地小助手**，专攻一件事：**什么时候该调工具、该调哪个、参数够不够**。

大多数小模型的工具调用只学会了两种模式——「看到工具就调」或者「照抄训练时见过的工具名」。
Rune1-Preview 训练的重点是**判断**：

| 场景 | 期望行为 |
|---|---|
| 用户给了完整参数 | **直接调**，不要再问一遍 |
| 用户漏了必填参数 | **反问**，不要瞎猜一个去试 |
| 两个工具都「能看文件」 | 按语义**选对**那个（按内容筛 vs 列目录） |
| 问题根本不需要工具 | **不调**，直接回答 |
| 调用报错了 | 读错误、**改对再来**，而不是放弃或硬编 |

它**不是**通用助手：复杂推理、长文档、算法设计都不擅长（1B 容量限制）。
它的定位是**自建 agent 里的「工具选择大脑」**。

## 二、发布版本与格式

**本版只发布一个格式：f16 完整版权重。**

| 格式 | 状态 | 视觉 | 说明 |
|---|---|---|---|
| **f16（safetensors）** | ✅ **已发布** | ✅ 完整 | 本仓库。可继续微调、可二次量化 |
| GGUF（Ollama / llama.cpp） | ❌ 未发布 | ❌ 无 | 转换已验证可行，但导出的 GGUF 不含视觉，与「最完整版本」定位不符 |
| MLX 4bit | ❌ **无法发布** | — | 底座架构 `minicpmv4_7` 不被 `mlx_lm` 支持（连最新 main 都没有） |

**为什么没有 MLX 版**：`mlx_lm` 的加载逻辑是
`importlib.import_module("mlx_lm.models." + model_type)`，而 `models/` 目录里只有
`minicpm.py` 和 `minicpm3.py`，没有 `minicpmv4_7`。Apple Silicon 用户请走 transformers
（MPS 实测可用，峰值内存 6.5 GB）。

**为什么没发 GGUF**：GGUF 转换本身没问题（llama.cpp 自 2026-10-17 起支持
`MiniCPMV4_7ForConditionalGeneration`），但我们的 LoRA **只训了文本主干**，
导出的 GGUF 里 `vision/vpm` 张量为 0 —— 是一个**纯文本模型**。
既然本次的定位是"只发最完整的那份"，就不单独发布残缺版。

> ⚠️ 一个容易混淆的点：GGUF 里 `general.architecture` 会显示成 **`qwen35`**，不是写错。
> MiniCPM-V 4.7 的文本主干是**混合线性注意力**（张量名里有 `blk.N.ssm_a`、
> `blk.N.ssm_conv1d.weight` 这套状态空间参数），llama.cpp 复用 `qwen35` 架构来承载它。

## 三、快速开始

### 3.1 环境

```bash
pip install "transformers>=5.18.0" torch accelerate
```

> **版本有硬要求**：底座要求 `transformers>=5.18.0`。低于这个版本会在加载时报
> 未知架构 `MiniCPMV4_7ForConditionalGeneration`。

### 3.2 最小可运行示例

```python
from transformers import AutoProcessor, AutoModelForImageTextToText

model_id = "whcl412/FinchAI-Rune1-Preview-f16"
proc = AutoProcessor.from_pretrained(model_id)
model = AutoModelForImageTextToText.from_pretrained(
    model_id, dtype="bfloat16", device_map="auto")

tools = [{"type": "function", "function": {
    "name": "list_files", "description": "列出目录内容",
    "parameters": {"type": "object",
                   "properties": {"path": {"type": "string", "description": "目录路径"}},
                   "required": ["path"]}}}]

msgs = [{"role": "user", "content": "看下 /var/log 里有哪些文件。"}]

text = proc.apply_chat_template(msgs, tools=tools, tokenize=False,
                                add_generation_prompt=True)
out = model.generate(**proc(text=[text], return_tensors="pt").to(model.device),
                     max_new_tokens=256, do_sample=False)
print(proc.tokenizer.decode(out[0], skip_special_tokens=True))
```

### 3.3 工具调用的输出格式是 XML

```
<tool_call>
<function=list_files>
<parameter=path>
/var/log
</parameter>
</function>
</tool_call>
```

**两个必须知道的点**：

1. **思考内容走 `reasoning_content`**，不在 `content` 里。宿主如果不处理这个字段，
   会把思考当成正文显示出来。
2. **它的判断力体现在「不输出」上**：参数不够时它不产生 `<tool_call>`，而是直接用
   自然语言反问；问题不需要工具时它也不调。宿主必须能处理"这一轮没有工具调用"的情况。

### 3.4 完整 agent 循环（可复制）

这一段处理了三个真实接入会踩的问题：XML 解析、思考字段、缺参数/不调工具的兜底。

```python
import re

CALL_RE = re.compile(
    r"<function=([A-Za-z_][A-Za-z0-9_]*)>\s*(.*?)\s*</function>", re.S)
PARAM_RE = re.compile(
    r"<parameter=([A-Za-z_][A-Za-z0-9_]*)>\s*(.*?)\s*</parameter>", re.S)

def parse_calls(text):
    """从模型输出里抽出工具调用。返回 [{'name':…, 'arguments':{…}}, …]"""
    out = []
    for name, body in CALL_RE.findall(text):
        args = {}
        for k, v in PARAM_RE.findall(body):
            args[k] = v.strip()
        out.append({"name": name, "arguments": args})
    return out

def strip_think(text):
    """去掉思考标签和偶发的游离 </think>"""
    text = re.sub(r"<think>.*?</think>", "", text, flags=re.S)
    return text.replace("</think>", "").strip()

# ── 调用 ──
msgs = [{"role": "user", "content": "看下 /var/log 里有哪些文件。"}]
resp = chat(msgs, tools=TOOLS)          # 你的推理封装
body = strip_think(resp.get("content") or "")
calls = parse_calls(body)

if not calls:
    # ★ 这是「判断」，不是失败：它要么在反问缺什么，要么认为不该调工具。
    #   直接把 body 交给用户，不要重试。
    return body

for c in calls:
    # ★ 分发前必须查注册表。模型偶发会吐出不在列表里的工具名（见「已知问题」）
    if c["name"] not in REGISTRY:
        return f"（模型想调用未知工具 {c['name']}，已忽略）"
    result = REGISTRY[c["name"]](**c["arguments"])
    msgs.append({"role": "assistant", "content": body})
    msgs.append({"role": "tool", "content": str(result)})
```

### 3.5 常见接入错误

| 症状 | 原因 |
|---|---|
| 输出是空的，或只有一句反问 | **正常行为**——它在等参数，或判断不该调工具 |
| 正文里混着 `身份问题，直接答…` 这类句子 | 那是 `reasoning_content`，被当成 `content` 了 |
| 输出里有个孤立的 `</think>` | 已知问题，宿主过滤即可（见第十节） |
| 报未知架构 | `transformers` 版本低于 5.18.0 |
| `TemplateError: No user query found` | messages 里没有 user 消息（只传了 system，或历史末尾是 assistant） |

## 四、实测性能

测试机：**MacBook Pro M4 / 10 核 / 16 GB**，MPS 后端。

| 项目 | 数值 |
|---|---|
| 权重体积 | **2.9 GB**（3,109,054,480 字节，bfloat16） |
| 加载后常驻内存 | ~3.1 GB |
| 训练/推理峰值 | **~6.5 GB**（进程 RSS 0.71 GB + MPS driver 5.79 GB） |
| 训练速度 | 2.2~3.5 s/样本（序列 ≤950 token） |
| 全量训练一轮 | 600 条 × 2 epoch ≈ **63 分钟** |
| 增量补课一轮 | 600 条 × 0.5 epoch ≈ **14 分钟** |
| 27 项验收全跑 | ~190 秒（含 base 对照） |

**怎么读这张表**：

- **峰值 6.5 GB 是「最长样本」决定的**，不是平均值。实测稳态 MPS 占用只有 3.0~3.4 GB，
  只有跑到 950 token 的那条样本时才会顶到 6.5 GB。
- 所以**提高内存上限并不危险**——瓶颈是单条最长样本，不是累积。反过来，
  上限给不够则会在某条长样本上直接 OOM。
- 16 GB 机器完全够用，留一半给系统还有余量。

## 五、核心能力：判断力

### 5.1 agent 任务的五个子类型

这是模型价值的来源。训练数据里 agent 类占 35%，内部分成五种子类型：

| 子类型 | 教什么 | 占比 | 典型长度 |
|---|---|---|---|
| `single` | 标准两步调用（列目录 → 聚合） | 25% | ~816 token |
| **`recover`** | **撞错 → 读错误 → 改对重试** | 20% | ~934 token |
| **`disambig`** | **两个工具都能"看文件"，按语义选对** | 20% | ~620 token |
| **`no_tool`** | **工具都在，但这个问题不该用它们** | 20% | ~498 token |
| **`ask_back`** / `ask_direct` | **缺参数才反问，给了参数就直接调** | 15% | ~502 token |

后三个子类型是治「见着工具就想调」的——这恰恰是真实 agent 最缺的判断力。

### 5.2 实测对比（微调前 vs 微调后）

同一份基座权重，靠切换 adapter 跑两遍，27 条探针：

| 组 | 微调后 | 基座 |
|---|---|---|
| **身份** | **3/3** | 0/3 |
| **留出沙箱**（训练时从未见过的工具） | **6/6** | 6/6 |
| 已训沙箱 | **6/6** | 6/6 |
| 不该调工具 | **3/3** | 3/3 |
| **缺参数反问** | **3/3** | 0/3 |
| **工具选择** | **3/3** | 0/3 |
| 通用（问答 / 代码 / 拒绝） | **3/3** | 3/3 |
| **合计** | **27/27** | 21/27 |

**净增量 = 判断力 +6、身份 +3。**

两个最有代表性的对比：

```
问：帮我看下目录里有什么文件。          （没给路径）
  微调后 → 「哪个目录？给我具体路径，我就去看。」   ✓ 反问
  基座   → 直接拿一个猜的路径去调了                  ✗

问：D:/inbox 里哪些文件提到 error？     （两个工具都能碰文件）
  微调后 → 调用搜索工具 seek_*                       ✓ 选对
  基座   → 调用列表工具 catalog_*                    ✗ 选错（但看起来"能跑"）
```

> 第二个例子值得单独说：**基座"选错工具"这件事，用宽松的判据是看不出来的**——
> 它毕竟调了本沙箱的工具。只有加了「参数名必须属于该工具的定义」这一层检查，
> 退化才暴露出来。**判据越松，越容易得到"看起来成功"的假象。**

### 5.3 留出沙箱与防泄漏

**留出沙箱 = 训练时结构上不可能产出样本的沙箱**（生成器里直接抛异常拦截）。

它的意义是给「数据有没有泄漏」一个硬指标：模型在那些**从未见过的工具名、路径、
参数 schema** 上也能正确调用，说明它学的是**「读工具定义、按语义选」**这个通法，
而不是把训练时见过的名字背下来。

实测它的思考是这样的：

```
工具叫 browse_mesa，参数只 need src。我填 /opt/mesa/inbox …
```

`browse_mesa` 是它训练时**从未见过**的工具。

## 六、能力边界

### ✅ 擅长

- **本地 agent 的「工具选择大脑」**——判断该不该调、调哪个、参数够不够
- **读一份没见过的工具定义并按它调用**（这是训练的核心目标）
- 简短、不谄媚的中文 / 英文回答
- 识别并拒绝违规请求（5 类场景：隐私 / 入侵 / 绕过保护 / 伪造身份 / 危险操作）

### ⚠️ 不擅长

| 短板 | 说明 | 规避方法 |
|---|---|---|
| 复杂多步推理 | 1B 容量限制，别指望它做算法设计 | 拆成小问题分步问 |
| 长文档理解 | 训练时序列 ≤950 token，更长的没测过 | 分段喂 |
| 视觉任务 | 底座支持图像输入，但**本版 LoRA 只训了文本主干** | 视觉能力未经强化，别当 VLM 用 |
| 跨句式泛化 | 训练覆盖内的句式很稳，完全没见过的说法可能掉线 | 见「已知问题」 |
| 无工具时算术 | 会算错 | 给它 `calculate` 类工具 |
| 超长上下文 | 底座支持 512K，但实际长文表现没测 | 别喂超长文档 |

## 七、怎么训的

### 7.1 沙箱式数据生成

每个训练样本来自一个**程序化生成的「沙箱」**，包含独立的：

- 工具名（`sweep_juniper`、`tally_atlas`、`catalog_kelp`…）
- 参数 schema（在 flat / nested / array / enum / optional 五种形状间轮换）
- 路径风格（`/var/lib/cedar_x`、`D:\inlet\files`、`/home/dev/kelp-2`）
- 错误消息风格（JSON / traceback / HTTP 422 / stderr 之间轮换）
- 语言与回答风格（中文 / 英文 / 混排）

**工具名是「语义槽词根 × 随机项目词」拼出来的**，故意的——让模型没法把某个名字和某个
行为绑死，只能真去读定义。

数据规模：**600 条**，六类配比：

```
agent 210 / code 120 / qa 90 / identity 60 / refuse 60 / multiturn 60
```

沙箱切分：**20 个训练沙箱 + 6 个留出沙箱**。

### 7.2 防泄漏六层

这是整个项目最较真的一块（"写漏了是无法挽回的"）。

| 层 | 机制 | 作用 |
|---|---|---|
| **L1** 命名空间物理隔离 | 词表按沙箱切分，用完即划归独占 | 工具名 / 路径 / 文件名**跨沙箱零共用** |
| **L2** 生成器硬拦截 | 给留出沙箱生成样本 → 直接抛异常 | **结构上不可能**产出，不是生成后过滤 |
| **L3** 渲染后 token 预算 | 真实 tokenizer 量，超限降级重试，再超丢弃 | 杜绝超长样本 |
| **L4** 渲染后文本审计 | 在 `apply_chat_template` 的**输出文本**上查标识符 | 抓跨沙箱串味 / 留出集混入 |
| **L5** 非 agent 样本禁含沙箱标识符 | code/qa 等类别不许出现任何沙箱名 | 防模板串味 |
| **L6** 参数名一致性 | 每次调用的参数名必须属于该工具的定义 | 防「数据自相矛盾」 |

**关键顺序**：**先切分、再生成**。留出沙箱的样本根本不会被生成出来。

写审计器时踩过两个坑，都值得记：

- **不能在 `json.dumps` 上做正则** —— `\n` 会把 `iris_02.txt` 切成 `niris_02.txt`（假泄漏）。
  必须审计 `apply_chat_template` **渲染后的文本**，那才是模型真正看到的。
- **不能做"谁都不属于"的猜测** —— 会把 `List`/`give`/`content` 全判成泄漏（上一版 213 处误报）。
  改成只对已知独占标识符判定 + 词边界。

一条设计原则：**工具名 / 路径 / 文件名独占**（带沙箱身份），
**通用参数名共享**（`dir` / `file` / `values`）。因为参数名是**可迁移约定**——
模型该学"读文件工具通常带 `file` 类参数"，而不是"某沙箱参数叫 xxx"。

### 7.3 训练配置

| 项目 | 值 |
|---|---|
| 环境 | `torch 2.14.1` / `transformers 5.20.1` / `peft 0.21.2`，MPS 后端 |
| LoRA | r=8, alpha=16, dropout=0.0，**仅文本主干**（整条路径排除 `vision`） |
| 可训练参数 | **7.47M（0.48%）** |
| 优化器 | AdamW，lr 1e-4（首轮）/ 5e-5（补课） |
| batch | 1，梯度累积 8 |
| 梯度检查点 | **必须开** |
| 内存上限 | `set_per_process_memory_fraction(0.90)` |
| 序列上限 | 950 token |
| 训练轮次 | 600 条 × 2 epoch = 150 步（有早停） |

**loss 只算 assistant 部分**：非 assistant 的 token 全 mask 成 `-100`，
否则模型会去学"怎么生成用户的话"。实测一条样本 239 token 里 **190 个参与 loss（79%）**。

### 7.4 防遗忘三件套（增量训练）

补课训练时，"不要让它忘了之前学的"靠三件事：

1. **数据保持完整六类配比**（不是只喂新样本，每训一条新样本同时也在复习旧能力）
2. **学习率减半**（1e-4 → 5e-5）
3. **只训 0.5 epoch**（37 步）

实测有效：**三轮补课，判断力始终 9/9，一次都没被冲掉。**

### 7.5 踩过的坑（按严重程度）

#### ① 参数名硬编码 —— 数据自相矛盾（最致命）

```python
工具定义：catalog_inlet → 参数名是 criteria
样本调用：{"dir": "D:/inlet/files"}    ← 生成器里硬编码的 dir
```

全量统计：**337 / 358 次调用与自己的定义对不上**。模型于是学到了
"调用就用 `dir`"这条错误规则，而不是"读当前工具定义的参数名"。
验收时留出沙箱从基座的 6/6 掉到 **2/6**。

修法：从工具定义里取真实参数名，修完 **356 一致 / 0 不一致**。

#### ② 身份数据全挂在 system 上

5 个身份变体**全都**带 system 里的身份声明，模型就学会了依赖它——
不传 system 时 3/3 全退回基座身份（答"我叫 MiniCPM"）。

这个坑跟上一代正好是**镜像**：上一代是"宿主给了 system 就忘了自己叫什么"，
这次是"宿主不给 system 就不知道自己叫什么"。**两个方向都得训。**
改成一半带一半不带（34 / 26），并补了英文变体。

#### ③ 句式覆盖不足

`ask_back` 的负样本只有「帮我看下目录里有什么文件」（不带路径）这一种说法，
模型就学成了触发词规则——**看到"帮我看下 / 搜一下 + 目录"就问**，哪怕路径就在句子里。

修法：给每个子类型加**句式池**（每类 4~5 种说法）。`single` 从此产出 49 种说法。
修完留出沙箱回到 6/6。

**教训**：判断力是对比出来的，**单边示范只会教出一个触发词**。

#### ④ refuse 场景太少

`REFUSE_CASES` 只有 3 条固定场景 + 一句固定答法，遇到第 4 类场景（查他人隐私）
就生成了语法不通的碎句。扩到 **5 类场景 × 19 种问法 × 3 种开头措辞**后修复。

#### ⑤ epoch 循环多跑一轮

```python
for epoch in range(int(args.epochs) + 1):   # epochs=2.0 时给出 3 轮
```

计划 142 步实跑 **253 步**，loss 被压到 0.0038 的严重过拟合。
修法：加 `if step >= total: break`。

#### ⑥ 训练中 OOM ≠ 内存泄漏

step 55 处 MPS 显存 OOM，第一反应是"泄漏"（因为崩时报 8.5G）。但把日志里每次打印的
显存值抽出来看：**3.06 / 3.08 / 3.06 / 3.39 / 3.39 / 3.08 / 3.05 / 3.06 / 2.99** ——
**全程平稳，根本没有累积**。

真相是**长样本的瞬时峰值**。数据长度是双峰的（非 agent 75~700，agent 900~950），
而 **31.5% 的样本都在 900~950 这个区间**，跳不过去。

修法三条：
1. **上限 0.90 → 1.00**（上限给够才是解药，我原本以为调小更安全，正好相反）
2. **每个 micro 都清显存**（不只在 step 边界清）
3. **加容错闸**：单条样本 OOM 就清显存、记一笔、跳过它继续跑

**教训**：单条探测的结论不能外推到连续训练——探测时进程是全新的、显存池干净，
训练跑到第 55 步时分配器已经有碎片，同样长度的样本就要不到连续块了。

#### ⑦ MPS 内存管理的三个反直觉点

| 做法 | 结果 |
|---|---|
| `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0` | **绝对不行**——取消上限，会把 16 GB 整机吃穿、系统卡死 |
| `=1.0` | 报 `invalid low watermark ratio`（与默认低水位 1.4 冲突） |
| **完全别碰它**，只用 `set_per_process_memory_fraction()` | ✅ 正确做法 |
| 调 `model.enable_input_require_grads()` | **内存杀手**——第一批反传就要不到 896MB 的 lm_head 梯度直接 OOM |
| 不调它，同样开梯度检查点 | ✅ 跑通 |

另外：**梯度检查点是决定性的**——
不开时 608 token 就 OOM，开了之后 608 token 只用 2.94 GB。

#### ⑧ LoRA 后缀匹配会误伤视觉塔

用后缀匹配（`q_proj`、`v_proj`…）会同时打中 `vision` 里的同名层，
第一次跑出 **187/374 无梯度**。必须按**整条路径**排除 `vision`。

#### ⑨ OOM 是断崖，不是斜坡

cap 55% 下实测：**667 token ✓ / 674 token ✗**。只差 7 个 token。
这意味着**样本长度必须用实测天花板来卡，不能估算**——估算出来的预算会在训练中途爆炸。

## 八、验收

`rune1_eval.py`：**27 条探针 / 7 组**，同时跑 tuned 和 base 做对照
（用 `model.disable_adapter()` 切换，不重复加载模型）。

| 组 | 探针数 | 测什么 |
|---|---|---|
| 身份 | 3 | 中英文问名字，**故意不带 system** |
| 留出沙箱 | 6 | 从未见过的工具上调用（泛化） |
| 已训沙箱 | 6 | 训练见过的，做对照 |
| 不该调工具 | 3 | 摆上无关工具，问常识题 |
| 缺参数反问 | 3 | 不给必填参数 |
| 工具选择 | 3 | 两个相似工具里选对 |
| 通用 | 3 | 问答 / 代码 / 合规拒绝 |

**判据**（比第一版严格得多）：

- **agent 组：工具名和参数名都必须对**——参数名必须属于该工具的定义
- **该拒绝的组：一个工具都不能调**
- **缺参数组：不调用 且 要反问**
- 汇总结论单独列出「判断力」合计，**这一行是微调唯一能证明价值的地方**

> 第一版判据只比对了工具名，结果 tuned 和 base 都判"6/6 通过"，
> **退化被完全掩盖**。是加了参数名检查才漏出来的。

## 十、已知问题

### 问题 1：没有 MLX 4bit 版

底座架构 `minicpmv4_7` 不被 `mlx_lm` 支持（0.31.3 和最新 main 都没有）。
Apple Silicon 用户请走 transformers + MPS。

### 问题 2：GGUF 版不含视觉

LoRA 只训了文本主干，导出 GGUF 时 `vision/vpm` 张量为 0。
本版未发布 GGUF；将来若要发，需额外用 `--mmproj` 导出视觉投影器。

### 问题 3：输出里有游离的 `</think>`

偶发一个孤立的闭合标签（不带开标签），属于 thinking 模板没对齐。
**规避**：宿主输出前 `text.replace("</think>", "")`。

### 问题 4：思考文案带模板生成痕迹

像"参数只 need src"这种中英混杂，是模板生成留下的。结构是对的（每段都带证据），
但措辞变化有限。扩规模前值得换更自然的生成方式。

### 问题 5：工具相关的两种幻觉

**① 工具名幻觉**：极低概率下会吐出**不在工具列表里**的工具名（实测 10 次里 0 次复现，
是个位数百分比）。**规避**：宿主分发必须查注册表，绝不直接执行。这条没有例外。

**② 工具结果不足时会编数字**：如果工具返回的信息不足以回答，它可能**直接编一个结果**，
而不是明说"信息不够"。

实测：问「目录里有几个 `.gguf` 文件」，它只调了 `list_files`（返回的是目录列表），
却直接答「**有 269 个**」——它根本没数过。

**规避**：让工具的返回**直接可得答案**。例如不要指望它"从列表里数个数"，
而是提供一个 `count_files(pattern, path)` 这类专用工具。这是 1B 模型的可靠边界。

### 问题 6：跨句式泛化有限

训练覆盖内的句式非常稳，但完全没见过的说法可能掉线。
例如「在 X 里搜一下报错相关的记录」这个说法在早期版本里没覆盖到，
模型会误判成"缺参数"而反问（它甚至在思考里引用了路径，却仍说"没给"）。
现已通过句式池缓解，但**未知句式仍有边界风险**。

### 问题 7：身份细节会补充编造

名字和底座名都能答对，但**追问细节时可能补一个不存在的来源**。

实测一次：

```
问：你叫什么名字？
→ 我是 FinchAI-Rune1-Preview，底座是 MiniCPM-V 4.7-1B，基于 OpenAI-Rune1-Preview 微调
                                                    ↑ 最后这句是编的
```

**规避**：把完整身份写进 system；或对身份类回答只采信「名字 + 底座」两项，其余不采信。

## 十一、排错速查表

### 工具调用

| 症状 | 原因 | 解法 |
|---|---|---|
| 模型不调工具，反而反问 | **可能在正常工作**：真缺必填参数 | 补上参数重问 |
| 模型不调工具，直接回答 | **可能在正常工作**：问题不需要工具 | 无需处理 |
| 吐出不存在的工具名 | 偶发幻觉 | 宿主查注册表，丢弃未知调用 |
| 参数名不对 | 已修复（v3 前的数据 bug） | 升级到当前版本 |
| 反复调用同一个工具 | 工具返回里没有它期待的信息 | 检查工具返回格式是否清晰 |

### 输出内容

| 症状 | 原因 | 解法 |
|---|---|---|
| 正文里混着"身份问题，直接答…" | 那是 `reasoning_content` | 正确读取字段 |
| 出现孤立 `</think>` | 模板未对齐 | 输出前过滤 |
| 中英混杂 | 思考文案的模板痕迹 | 已知问题，不影响功能 |
| 回答很长 | 应该不会——身份类回答实测只有一句 | 检查是否把思考当正文 |

### 部署

| 症状 | 原因 | 解法 |
|---|---|---|
| `Unknown architecture MiniCPMV4_7…` | transformers 版本过低 | `>=5.18.0` |
| MPS 上 OOM | 内存上限给小了 / 没开梯度检查点 | 上限 0.90，开 `gradient_checkpointing_enable()` |
| 整机卡死 | 设了 `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0` | **删掉这行**，只用 `set_per_process_memory_fraction` |
| 微调时只有部分层有梯度 | LoRA 目标含 `vision` | 按整条路径排除 `vision` |
| 加载后答非所问 | 没套 chat template | 用 `apply_chat_template(..., add_generation_prompt=True)` |

### 一句话诊断流程

```
不调工具？
  ├─ 它在反问？ → 正常（缺参数）
  ├─ 它在直接答？ → 正常（不需要工具）
  └─ 都没有，内容为空 → 检查 reasoning_content 字段
答非所问？
  └─ 检查是否套了 chat template
调用出错？
  └─ 检查工具名是否在注册表里（防幻觉）
```

## 十二、常见问题

**Q：该下哪个格式？**
A：只有一个——本仓库的 f16。没有 MLX 版，也没有发布 GGUF。

**Q：能商用吗？**
A：可以。Apache 2.0，跟基座 MiniCPM-V 4.7-1B 一致。

**Q：它是多模态模型吗？**
A：底座是，**本版 LoRA 不是**。视觉能力没被训练到，只有 f16 权重保留着底座的视觉塔。
要跑视觉任务建议直接用原始底座。

**Q：怎么继续微调？**
A：用 `transformers + PEFT`（不是 MLX）。训练脚本和数据都在 GitHub 仓库里，
`scripts/rune1_train.py` 可直接改用。**注意 `transformers>=5.18.0`**。

**Q：为什么不用 MLX？**
A：`mlx_lm` 不支持 `minicpmv4_7` 架构。详见第二节。

**Q：它说自己是 MiniCPM 怎么办？**
A：那是基座身份。本版已修复（不依赖 system 也能答对），若仍出现，
在 system 里写明"你是 FinchAI-Rune1-Preview"。

**Q：上下文能多长？**
A：训练时序列 ≤950 token，**实际有效上下文以这个为准**。底座支持更长，但没测过。

**Q：为什么叫 Preview？**
A：判断力已达标（9/9），但句式泛化和拒绝场景仍在扩充。这是首个 FinchAI 模型。

**Q：训练数据用的什么？**
A：**全部是程序化合成的**，不含任何真实用户数据。结构和生成器都在 GitHub 上开源。

**Q：重训一轮多久？**
A：全量 2 epoch 约 63 分钟（M4 / 16 GB）；增量补课 0.5 epoch 约 14 分钟。
